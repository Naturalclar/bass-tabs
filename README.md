# bass-tabs

MusicXML を読み込んで、**A4 にきれいに印刷できる楽譜**を表示するビューア。
ベース練習用の譜面を紙で用意することが目的。

Vite + React + TypeScript / 描画は [OpenSheetMusicDisplay](https://opensheetmusicdisplay.org/) (OSMD)。

## これは何ではないか

画面で弾きながら追う用途（再生・カーソル追従・テンポ変更・区間ループ）は**対象外**。
このサイトは印刷物を出すためのもので、そちらの用途は alphaTab で別途検討する。

## 公開先

<https://naturalclar.github.io/bass-tabs/>

`main` に push すると `.github/workflows/pages.yml` がビルドしてデプロイする。
ファイルはブラウザ内でのみ処理されるので、サーバ側の処理は無く静的配信で足りる。

project site なので配信パスは `/bass-tabs/`。この文字列は `base-path.ts` に 1 箇所だけ置いて、
Vite の `base` と Playwright の遷移先の両方がそこを参照している（片方だけ直す事故を防ぐため）。
`pnpm dev` も同じパスで動く（<http://localhost:5173/bass-tabs/>）。dev と本番で
パスの解決を変えないため、意図的にそうしている。

**リポジトリ側の設定**: Settings → Pages の source を「GitHub Actions」にしておく必要がある。

**デプロイは CI の成否では止まらない。** Pages と CI は別ワークフローなので `needs:` で繋げない。
Pages 側のビルドは `pnpm build`（typecheck 込み）なので型エラーとビルド失敗は止まるが、
lint と print チェックの失敗はデプロイを止めない。困るようなら `workflow_run` で繋ぐ。

## 使い方

```sh
pnpm install
pnpm dev        # 開発サーバ (http://localhost:5173/bass-tabs/)
```

パッケージマネージャは **pnpm**。バージョンは `package.json` の `packageManager` で固定してあるので、
corepack 経由なら合わせる必要は無い。`node_modules` は既定の非フラット構成のままにしている
（巻き上げに頼った参照を許すと、CI と手元で解決結果が変わる余地を残すことになるため）。

依存のビルドスクリプトは既定で全て実行しない（`pnpm.onlyBuiltDependencies` が空）。npm では
OSMD の依存の `gl`（headless-gl、ネイティブビルド）がビルドされていたが、このアプリは
ブラウザで SVG バックエンドを使うだけでネイティブモジュールを読まないので不要。
`pnpm.ignoredBuiltDependencies` に挙げて、警告ではなく意図として記録してある。

サイトを開くと、**最初から自分の譜面が編集できる状態で出る**（前回開いていた譜面。初回は
空の譜面）。手持ちのファイルが無くてもそのままタブ譜を書き始められて、書いたものは印刷でき、
`.musicxml` として書き出せる。

手持ちのファイルを見たいときは「ファイルを開く」で `.xml` / `.musicxml` / `.mxl` を選ぶ →
A4 縦に組まれた楽譜が出る → 「印刷」。サーバもアップロードも無く、ファイルはブラウザ内で
のみ処理される。ヘッダの「譜面を作る」はエディタ表示のトグルで、押すとファイル表示との間を
行き来する。

## 譜面を作る

拍子・調・小節数を決めて、弦とフレットと音価を置いていく。編集内容は `localStorage` に
保存されるので、閉じても消えない。

左のサイドバーに保存済みの譜面が並ぶ。「＋ 追加」で新しい譜面を作り、行をクリックで切り替える。
**譜面を消すと取り消せない**（取り消し履歴は譜面の中の編集を対象にしていて、譜面そのものの
出し入れは覚えていない）ので、削除には確認を挟んでいる。最後の 1 つを消すと空の譜面が残る。

入力方法は 3 つ:

- **クリック** — タブ譜のレーンを押すと、選んでいる音価とフレットでそこに音が入る
- **キーボード** — 数字でフレット（続けて押すと 2 桁: `1` `2` で 12 フレット。ただし
  2 桁にすると存在しないフレットになる組み合わせは次の音: `3` `3` は 3 フレット 2 つ）、
  `↑↓` で半音上下、`Shift+↑↓` で弦の持ち替え、←→ でカーソル、`Shift+←→` で小節移動、
  `w` `h` `q` `e` `s` で全/2分/4分/8分/16分、`.` で付点、`r` で休符、
  `Backspace` で削除、`Ctrl/⌘+Z` で取り消し、`Ctrl/⌘+Shift+Z`（または `Ctrl+Y`）でやり直し
- **MIDI キーボード** — 「MIDI キーボードを使う」を押すと Web MIDI API 経由で接続する。
  弾いた音は**最も低いフレットで押さえられる弦**に割り当てられる

**MIDI は動かない環境がある。** Web MIDI API はブラウザによって非対応で、かつ secure context
（https か localhost）が必要。非対応・拒否された場合はボタンにその旨が出るだけで、
他の入力方法には影響しない。

### 音を置いたあとに動かす

`↑↓` は**選択中の音を半音ずつ**動かす。押さえる位置が同じ弦に収まるうちはその弦に留まり、
フレットが端（0 / 24）を越える場合だけ、**同じ音が出せる隣の弦へ運ばれる**。
ベースで出せない音（E1 より下）まで下げようとしたときは何も起きない。

`Shift+↑↓` は**音を変えずに弦だけ**持ち替える（E 弦 5f ⇄ A 弦 0f）。
その弦で出せない音のときは動かない。選択中の音が無いときは、次に置く音の弦を選ぶ。

小節が拍子ぶんで埋まると、**その小節の追加用の列（`+`）は表示されなくなる**。押しても拒否
されるだけの列を出しておく意味が無いため。強調表示はその小節の最後の音に残る。

動かす対象はタブ譜で強調表示されている列。音を置いた直後はその音が対象になる。
連続した移動は取り消し 1 回でまとめて戻る。

### 小節をまたぐ入力

小節が埋まったまま打ち続けると、**音は次に空きのある小節へ流れる**。フレーズをひと続きに
打ち込んでいる最中に、小節線で入力が黙って止まるより自然なため。

最後の小節を超えたときは**小節が 1 つ増えて、その音がそこに入る**。増えるのは音を書いた
ときだけで、カーソル移動では増えない — だから増えた小節は必ず音を持っていて、末尾に空の
小節が残ることはない。音と小節は取り消し 1 回でまとめて戻る。上限は 64 小節。

すでにある音の打ち替えは流れない。書いた場所を変えてしまうため、収まらなければ拒否する。

### 書き出しと取り込み

譜面はブラウザの中にしか無いので、サイトのデータを消せば消える。サイドバー下部から**一覧ごと
JSON に書き出せる**。同じファイルを「取り込む」で戻せる。

取り込みは**常に追加**で、既にある譜面は消さない。復元のつもりで押しても、手元の作業が失われる
ことはない。書き出した MusicXML（TAB 譜を含むもの）も同じ口から一覧に取り込める。

読めないファイルは取り込まず、理由を表示する。保存データと同じ検査を通しているので、
壊れたファイルでアプリが起動しなくなることはない。**エディタが持てない内容も取り込まない**:
和音・タイ・装飾音入り、65 小節以上、拍子に収まらない小節のあるファイルは理由を出して断る
（半端に取り込むと、保存できずにリロードで消えたり、元と違う譜面になったりするため）。
表示だけなら「ファイルを開く」からできる。

**`.mxl`（圧縮）は一覧への取り込みには対応していない**（解凍を持っていないため）。表示だけなら
「ファイルを開く」から可能。

### 動画から取り込む

ヘッダの「動画から取り込む」で動画モードに入る。YouTube のリンクを貼ると埋め込みプレイヤーが
出るので、**「画面共有を開始」でこのタブを共有し、タブ譜が映ったところで「今の画面を読み取る」**
を押すと、認識した音が今の譜面の末尾に足されていく。1 回の読み取りは 1 手なので `Ctrl+Z` で
1 回ぶん戻せる。

画面共有を挟むのは、埋め込み動画のピクセルがクロスオリジンで、`getDisplayMedia` 以外に読む
手段が無いため。共有はこのモードを出ると必ず止まる。動画モードでは譜面の表示を隠している —
キャプチャは自タブを映すので、画面内の五線や TAB 譜が「弦の線」として誤検出されるため。

読み取りの中身はスクリーンショット取り込みと同じ（下記）。**リズムは推定しない**ので、
タブ譜の行が切り替わるたびに読み取り、最後にエディタで音価を直す使い方になる。

**タブ譜のスクリーンショット (PNG/JPEG/WebP) も同じ口から取り込める。** 4 本の弦の線を見つけ、
線上のフレット数字を OCR (tesseract.js) で読んで譜面にする。動画のオーバーレイ（黒地に白）も
紙面風（白地に黒）も同じに扱う。**音価は推定せず全部 8 分音符**で置くので、リズムはエディタで
直す前提（読めなかった数字は消える代わりに休符になり、件数を表示する）。弦の線が 4 本見つから
ない画像、同じ位置に複数の弦の数字がある画像（和音）は理由を出して断る。OCR のアセット
（worker / wasm / 言語データ、計約 6MB）は `public/ocr/` からセルフホストし、画像を取り込む
ときだけ遅延読み込みする — CDN には依存しない。

### 取り消し

編集は 50 手まで遡れる。小節数を減らす・「新規」を押すといった、まとめて捨てる操作も取り消せる。

曲名の入力と、2 桁のフレット入力（`1` `2` で 12 フレット）は**まとめて 1 手**として扱う。
1 文字・1 打ごとに戻ると使いものにならないため。

**曲名などの入力欄にフォーカスがあるときは、譜面ではなくその文字入力が戻る**（ブラウザ標準の挙動）。
履歴は保存しないので、リロードすると消える。

### 記譜のオクターブ

ベースの慣習どおり、**五線譜は実音より 1 オクターブ高く書いている**。実音のまま書くと E 弦の
開放が加線 3 本ぶん下に沈んで読めない（同梱サンプルで測ると加線の要素数が 201 対 10）。

書き出す MusicXML には `<transpose>` で「実音は 1 オクターブ下」と宣言しているので、
**他のソフトで開いても鳴る音は正しい**。OSMD はこの宣言を表示に反映しないため、
表示は上げたまま・ファイルの意味は正確、という両立ができている。

TAB 側のフレット番号は変わらない。押さえる場所の話なので当然だが、検査でも見ている。

### 対応している範囲

4 弦ベースのレギュラーチューニング（E1-A1-D2-G2）固定。1 音ずつの単音のみで、**和音・タイ・
連符・繰り返し記号・強弱記号には対応していない**。小節は拍子ぶんを超えて入力できず、
足りないぶんは書き出し時に休符で埋められる。

作った譜面は**取り込んだファイルと同じ経路**（`src/score/useOsmd.ts`）で描画される。
つまり A4 の組版も印刷も、取り込んだ譜面とまったく同じものが効く。

`public/samples/` に動作確認用の譜面が入っている（通常譜・TAB 譜・圧縮 `.mxl`）。

## スクリプト

| コマンド | 内容 |
| --- | --- |
| `pnpm dev` | 開発サーバ |
| `pnpm build` | `typecheck` してから本番ビルド |
| `pnpm preview` | ビルド結果の確認 |
| `pnpm lint` | oxlint（警告も失敗扱い） |
| `pnpm typecheck` | `tsc -b --noEmit` |
| `pnpm check` | lint + typecheck。CI はこれに加えてビルドと `pnpm test:print` も走らせる |
| `pnpm test:print` | 印刷リグレッションチェック（ビルド → 配信 → PDF 出力まで実行） |

### なぜ oxlint と tsc の両方なのか

oxlint は速度を理由に選んでいるが、型情報を使う検査（typescript-eslint の型付きルール相当）を
完全にはカバーしない。その層は `tsc` で埋める。**片方だけでは足りない**という実例が実際に出た:
`backend: BackendType.SVG` は oxlint を素通りしたが `tsc` が拒否した（OSMD 2.1.2 の `backend` は
`string` 型で、数値 enum の `BackendType` は代入できない。正しくは `backend: 'svg'`）。

oxlint は `--deny-warnings` で動かしている。既定では警告があっても終了コードが 0 になるので、
`warn` に設定したルールが CI を落とせない。実際、レンダー中の ref 参照と effect 内の同期的な
`setState` の警告が出たまま CI が green だったことがある。手元と CI で同じコマンドを使うため、
別スクリプトを足すのではなく `pnpm lint` 自体を厳しくしてある。

## 印刷リグレッションチェック

```sh
pnpm test:print
```

印刷結果はこのアプリの成果物そのものだが、oxlint も `tsc` も見ることができない
（ページ数は OSMD の改ページ、紙のサイズはプリンタが解決する CSS が決めるため）。
そこで Playwright で実際にビルド・配信・PDF 出力まで通して検査する（`tests/print.spec.ts`）。
サーバは設定側で起動するので、事前に `pnpm dev` を動かしておく必要は無い。

検査している内容と、それぞれが**どの不具合を捕まえるか**（いずれもコードを壊して
対応するテストが落ちることを確認済み）:

| 検査 | 捕まえる不具合 |
| --- | --- |
| PDF のページ数と `/MediaBox` (≈210×297mm) | ページラッパーの shrink-to-fit による再ページング（2 ページが 4 ページになる） |
| `score-page--break-after` が最終ページ以外に付いているか（DOM を直接検査） | 改ページ指定の消失。**ページ数では検知できない** — 各サンプルはちょうど 297mm × 2 ページなので、改ページを消しても自然フローで 2 枚に収まってしまう |
| 画面表示時のページ幅（印刷時だけでなく） | 300px への潰れ。これは**画面側**の不具合で、印刷時は `.score-page` が `210mm` 固定のため印刷側だけ測っても素通りする |

`@playwright/test` はキャレット範囲ではなく**バージョン完全固定**にしている。
対応する Chromium ビルドが変わると測定値の前提が変わるため。
CI では `check`（lint / typecheck / build）とは別ジョブで走る。

## 印刷設計

- **SVG バックエンド固定。** Canvas はラスタなので画面では同じに見えても印刷で音符の縁がぼやける。
  SVG ならプリンタ解像度でそのまま出る。
- **ページ分割は OSMD にやらせる。** `pageFormat: 'A4_P'` を指定すると OSMD がページ単位に組み、
  1 ページ = 1 個の `<svg>` として出力する。CSS の改ページ任せにすると段の途中で切れる。
- **紙のサイズは CSS が一度だけ宣言する。** レンダリング後に各ページ `<svg>` の `width`/`height`
  属性を `viewBox` に置き換えているので、画面では可変幅・印刷では `210mm × 297mm` と、
  再レンダリング無しでサイズを変えられる（`src/score/useOsmd.ts` の `makePagesScalable`）。

## 実機で確認した結果 (2026-08-20, OSMD 2.1.2 / Chromium 1194)

Chromium で実際に読み込み・印刷（PDF 出力）まで通して確認した。

### OSMD のオプション名（バージョンで変わりうるので実測値）

| 指定 | 値 | 備考 |
| --- | --- | --- |
| `pageFormat` | `'A4_P'` | **アンダースコア区切り**。`OpenSheetMusicDisplay.PageFormatStandards` に `A4_P` = 210×297mm として定義。`'A4 P'` ではない |
| `backend` | `'svg'` | 型は `string`。`'svg'`/`'SVG'`/未指定以外は Canvas になる |
| `drawingParameters` | `'default'` | |
| `disableCursor` | `true` | 再生しないのでカーソル要素は不要 |
| `autoResize` | `false` | true だとウィンドウリサイズのたびに再レンダリングして固定幅と競合する |

`osmd.load()` は `Blob` を直接受け取り、`.mxl` の解凍も内部で行う（JSZip 同梱）。
そのため `.xml` と `.mxl` で読み込み経路を分ける必要は無かった。

### A4 指定とブラウザの印刷縮尺

噛み合う。`@page { size: A4 portrait; margin: 0 }` + ページ `<svg>` を `210mm × 297mm` で、
Chromium の PDF 出力は **209.9 × 297.0 mm**（= A4）になった。

`@page` の余白を 0 にしているのは、**OSMD が自前のページ余白を持っているため**。実測で
左右約 13mm・上 12〜13mm・下 17mm 以上あり、一般的なプリンタの印字可能領域に収まる。
したがって印刷ダイアログの倍率は「実際のサイズ / 100%」を選べばよく、
「用紙に合わせる」で数 % 縮んでも内容が切れることはない。

### TAB 譜（タブラチュア）

**実用になる。** 「五線譜のみ対応」と割り切る必要は無かった。
TAB クレフ、4 線譜、フレット番号、`staff-tuning` によるチューニング反映、
通常譜との 2 段組み（`<staves>2</staves>` + `<clef number="2"><sign>TAB</sign>`）が
いずれも正しく描画される。OSMD 2.1.2 は `TabKeySignatureRendered` / `TabBeamsRendered` /
`TabTupletsBracketed` など TAB 専用の調整ルールも持っている。
確認は `public/samples/bass-tab.musicxml`（4 弦ベース E1-A1-D2-G2）で行った。

### 複数ページ時の調号・拍子の再掲

- **調号と音部記号は再掲される。** 2 ページ目冒頭（54 小節目）にヘ音記号とシャープ 3 つが出る。
  DOM 上でも 1 ページ目 8 システム / 調号 8・音部記号 8、2 ページ目 9 システム / 調号 9・音部記号 9 と、
  全システムに付いている。
- **拍子記号は再掲されない。** 曲頭に 1 個だけ。これは通常の浄書慣習どおり（拍子は変化時のみ再掲）
  なので、そのままにしてある。

### 実装上つまずいた点（DOM 構造に依存する箇所）

OSMD は各ページ `<svg>` を**それぞれ専用のラッパー `<div>` に入れる**。ここから 2 つ問題が出た。
どちらも修正済みだが、OSMD 更新時に再発しうるので記録しておく。

1. ラッパーが shrink-to-fit すると（例: 親を `align-items: center` にする）、`viewBox` 化した
   `<svg>` には固有サイズが無いため置換要素の既定値 300px に潰れ、`width: min(100%, 210mm)` の
   `100%` がその 300px を基準に解決されてしまう。→ ラッパーを常に全幅にしている。
2. 各 `<svg>` が別々の親を持つので、CSS の `:last-of-type` が**全ページにマッチ**する。
   「最後のページだけ改行しない」を CSS で書くと全ページの `break-after` が消え、
   PDF のページ数が壊れる。→ 改ページは JS 側でインデックスを見てクラス付与している。
